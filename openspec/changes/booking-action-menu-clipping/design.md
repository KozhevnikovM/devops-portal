## Context

See `proposal.md` for the reported behavior. `/book/vm` and `/book/namespace` both render `partials/booking_list_section.html`, which wraps the table in an `overflow-x-auto` div; any element absolutely positioned inside it is also clipped vertically. Each `partials/booking_row.html` row can show one of three `<details>` menus (READY/FAILED manage, admin in-flight Delete, QUEUED). Their direction comes from `is_first_row` (first row opens down, the rest open up), so the last rows near the bottom and any row in a short or scrolled viewport can still be clipped, and the list-rendered row differs from the refreshed row.

#538 fixed the same problem for environments: the menu became a native popover (top layer, so no ancestor overflow clips it), and `frontend/js/environment_menu.js` anchors it to its trigger, clamps it to the viewport, caps its height with internal scrolling, re-anchors on scroll/resize, hides it when the trigger leaves the viewport and disposes listeners when an HTMX/SSE swap removes it. It is keyed on `data-environment-menu` / `data-environment-menu-trigger`.

**Centred-menu failure (PR #543 review).** A native popover's UA style is `position: fixed; inset: 0; margin: auto`, which centres it in the viewport. Only the controller replaces that. A Chromium probe on the real `environment_row.html` markup gave:
- script served → the menu's top is 4 px below its trigger on the first, middle and last rows;
- script returning 404 → the menu is centred in the viewport on every row.

The controller logic is sound; the failure is delivery, a skew between templates and static assets:
- **Static assets come from a named volume filled by `init`.** In both `docker-compose.yml` and `docker-compose.prod.yml`, app/worker mount `portal_static:/app/app/static`, which hides both the image's and any bind-mounted host `app/static/`. `init` fills the volume on each run with `cp -r /app/app/static/. /static/` from *its own image*. The copy only adds and overwrites; it never deletes.
- **In dev, templates and assets come from different builds.** `.:/app` makes `base.html` current immediately, so after #540 it references `environment_menu.js`. The volume holds what the last-built `init` image shipped, and `docker compose up` without `--build` reuses that image. Here the `init` image dates from 2026-09-30 and the volume was last filled on 2026-10-06. It lacks `environment_menu.js`, `row_reconcile.js` and `environment_deployment.js`, so the menu is centred. Running a host-side build would not help, because the volume hides the host directory.
- **In prod**, Ansible runs compose with `build: always`, so `init` is rebuilt and re-run every deploy. A manual `docker compose -f docker-compose.prod.yml up -d` without `--build`, or rebuilding only one service, has the same skew. `init`, app, worker and beat each build their own image from the same context, so one of them can be current while another is stale.
- **Nothing detects it.** `/health/ready` checks only Postgres and Redis. The Docker smoke test never renders a `base.html` page; `/auth/login` is a standalone template that loads only `tailwind.css`. The Dockerfile copies each `frontend/js` file by name. The browser tests inject the script with `add_script_tag`, assert only viewport containment, and `importorskip` Playwright, which no CI job installs.

## Goals / Non-Goals

**Goals:**
- One shared controller and one markup pattern for row action menus, used by environment and booking rows.
- Booking rows render identically wherever they come from (list, Load more, single-row refresh, SSE, reconcile).
- A menu is anchored to its trigger even when the controller script is missing; a missing script fails CI.
- The browser regression suite runs in CI and cannot pass by skipping.

**Non-Goals:**
- Admin Catalog tables and the `☰` nav / roles dropdown `<details>` (not row menus in a scrolling list, or not reported).
- Changing any action, permission check, confirmation text or HTMX target.
- Removing the dev compose bind mount or the `portal_static` volume. The volume exists because of the bind mount (`docs/bugfix/static-dir-missing-on-volume-mount.md`) and is shared by the blue and green slots.

## Decisions

- **Generalise rather than copy.** Rename `environment_menu.js` to `row_menu.js` and key it on neutral attributes (`data-row-menu` on the popover, `data-row-menu-trigger` on its button). Environment rows switch to the new attributes. Alternative — a second `booking_menu.js` — rejected: two copies of the same lifecycle code would drift, and the issue asks for a reusable fix.
- **The controller is the primary placement and keeps its rules.** It opens below the trigger when the menu fits there, otherwise on the roomier side, right-aligned to the trigger and clamped to the viewport, with height capped to the available room. It stays hidden (`visibility: hidden` from `beforetoggle`) until the first `position()`, so there is no centred first frame. The review's acceptance criteria (prefer below, flip above, never centred, on screen, re-anchor on scroll/resize) already describe these rules; the change makes them required and tested, not different. Review the code paths that could leave UA placement visible (an exception in `attach`/`position`, a toggle missed by the capture listeners, a trigger lookup returning null) and make each one fail toward the CSS fallback below rather than the centre.
- **CSS anchor fallback, independent of the script.** A small non-Tailwind `<style>` block in `base.html` (same pattern as the `.kv-*` editor styles, so purge can't drop it) gives `[data-row-menu]` `margin: 0; inset: auto` and anchors it to its trigger with CSS anchor positioning: each trigger gets `anchor-name: --row-menu-<id>`, the popover gets `position-anchor` plus `position-area: block-end span-inline-start` and `position-try-fallbacks: flip-block`. With the script loaded, the controller overrides the fallback with inline `position-area: none` and `position-try-fallbacks: none` on attach, before measuring or setting `top`/`left`. Merely clearing the inline value (`= ''` or `removeProperty`) leaves the stylesheet's `position-area` in effect, and `top`/`left` then become offsets from the anchored area rather than viewport coordinates. A Chromium probe confirmed it: `top: 10px` landed at y=230 with the rule still applied and at y=10 with inline `none`. Overriding `position-try-fallbacks` too stops `flip-block` from swapping the controller's insets while it measures the menu's natural height. On close the controller leaves the inline overrides in place; they are harmless because only the controller opens menus when it is loaded. Without the script, the menu still opens beside its button and flips near the bottom; it may lack height capping, which is acceptable for a degraded path. Alternative: hide unpositioned menus with CSS until the script marks them — rejected, because a missing script would then make every action unreachable, which is worse than the current bug. Where a browser lacks anchor positioning the fallback degrades to the UA default, and the asset gate below is what prevents the missing script.
- **Same markup in every booking menu variant.** Each of the three `<details>` blocks becomes a `<button popovertarget>` plus a `<div popover data-row-menu>` holding the existing contents verbatim. IDs follow the environment pattern (`booking-<id>-menu`, `booking-<id>-menu-trigger`) so they are unique per row and the focus hand-back finds the replacement trigger after a swap. A shared Jinja macro for the trigger/popover shell (including the anchor style attributes) keeps environment and booking rows identical.
- **Drop `is_first_row`.** The controller picks the direction from the trigger's viewport rectangle, so the list templates stop setting it and the row stops reading it.
- **Popover stays inside the row in the DOM.** `hx-target="closest tr"` and `#booking-<id>` targets inside the menu keep working, and a row swap removes the popover with the row; the controller's MutationObserver already handles that disposal.
- **Scripts always ship, and skew is loud.**
  - **Readiness check, evaluated live.** Every `GET /health/ready` scans the page templates (every `.html` under `app/presentation/templates/`, which covers `base.html`, the standalone `login.html` and any partial) for same-origin `/static/...` references, query string stripped, and checks each one exists under the mounted static directory. The scan is cached per template file and re-parsed only when that file's mtime changes; asset existence is re-checked on every call. The per-call cost is roughly 40 template `stat`s plus one `stat` per referenced asset, which is negligible at readiness-poll rates. A cached-at-startup result is rejected: the dev bind mount makes template edits live without a restart, because Jinja's `auto_reload` re-reads them while `uvicorn --reload` watches only Python files and Compose doesn't recreate an unchanged container. A startup-only check would therefore report 200 while the live page requests a missing script, which is exactly the failure behind this bug. Scanning instead of keeping a hand-maintained list means a new `<script src>` is covered automatically. Missing files make `/health/ready` return 503 with a `static_assets` check naming them. They are also logged as an ERROR at startup and whenever the set of missing assets changes, not on every poll. The blue-green deploy polls readiness, so a slot with a stale volume is never cut over, and a dev developer sees the cause immediately. **Limitation:** the check verifies existence only. If a script's content changes but its filename stays the same, the stale copy in the volume is still served and readiness stays 200; this gate catches a *new or renamed* reference (as #540's `environment_menu.js` was), not content skew under an existing name. Content verification, such as a build hash written by `init` and compared by the app, is out of scope: under the dev bind mount the app has no build of its own to compare against. `docker compose up --build` remains the documented refresh path, and `docs/admin-guide.md` states this limit.
  - **One image for every compose service.** In both compose files, `init`, the app service(s), worker and beat use the same `image:` tag (overridable, default per file) with the same `build:`. Rebuilding any one of them refreshes the image `init` copies from, and Compose recreates `init` on the next `up` because its image changed.
  - **`init` stays additive.** It keeps copying without deleting, so during a blue-green cutover the old slot's templates still find the old files. A renamed script such as `environment_menu.js` lingers harmlessly in the volume. `init` gains a check that the copied static directory matches its image, so a partial copy fails the one-shot and blocks dependent services.
  - **Documented refresh path.** `CLAUDE.md` and `docs/admin-guide.md` say that frontend or template changes under compose need `docker compose up --build`, which rebuilds the shared image and re-runs `init`. The readiness check catches it when that is skipped. An end-to-end compose check (task 4.4) verifies `GET /static/js/row_menu.js` returns 200 and that the Environments menu is anchored on the compose-served page.
  - **Whole-directory copy.** The Dockerfile copies the whole built `dist/js/` directory instead of one `COPY` per file, so a new script can't be left out of the image.
  - **Without Docker.** `package.json` gains a `build:static` script (Tailwind build, htmx vendor copy, `frontend/js/*.js` copy into `app/static/`) for running `uvicorn` directly. `CLAUDE.md` replaces the Tailwind-only command with it. It has no effect on compose, which serves the volume.
  - **Smoke test.** The production container already seeds an admin (`ADMIN_PASSWORD=smoke-test-admin`). The smoke test logs in with `POST /auth/login`, sending an `Origin` that matches `BASE_URL` for the CSRF check. It then fetches `/environments`, `/book/vm` and `/auth/login` and requests every same-origin `<script src>` / `<link rel=stylesheet>` they reference, failing on any non-200 and naming the asset. It also asserts `/health/ready` reports `static_assets` as ok. A negative step then removes `app/static/js/row_menu.js` from the running container (`docker exec -u root`, since the files are root-owned) and expects both the asset check and readiness to fail. No restart is needed, since readiness is evaluated live; the step deliberately doesn't restart, which also proves live detection.
- **Mandatory browser CI.** A new `browser-tests` workflow installs `requirements-dev.txt` plus a new `requirements-browser.txt` (pinned `playwright`), runs `playwright install --with-deps chromium`, and runs `pytest -m browser` with `REQUIRE_BROWSER_TESTS=1`. In the browser fixtures, that variable turns the Playwright import and launch skips into failures, and a `pytest_terminal_summary`/`--strict` guard fails the run if any `browser` test was skipped. The `browser` marker is excluded from `fast-tests`, which stays free of Playwright. `scripts/audit_python.py` is extended to audit `requirements-browser.txt`.
- **Tests load the page the way production does.** The fixture serves a page whose `<head>` loads `/static/js/row_menu.js` and the built stylesheet through `<script src>` / `<link>` routed to the repo files, rather than `add_script_tag`. One case routes the script to 404 and asserts the CSS fallback keeps the menu beside its trigger. Geometry assertions: menu top within a few px below the trigger's bottom (or menu bottom just above its top when flipped), horizontal overlap with the trigger, fully inside the viewport, and no animation frame between click and settle where the menu is visible at the viewport centre (rects recorded per `requestAnimationFrame` from the click).

## Risks / Trade-offs

- [Renaming the script breaks a cached `environment_menu.js` reference] → Rename in `base.html` and the Dockerfile in the same change; static assets are build artifacts, so no stale copy ships.
- [CSS anchor positioning support differs by browser] → It is only the fallback; the controller remains the primary placement, and the smoke-test asset gate prevents the missing-script case in the image. The browser test for the fallback runs in Chromium.
- [The CSS fallback fights the controller] → The controller sets inline `position-area: none` and `position-try-fallbacks: none` on attach (clearing is not enough), then sets explicit coordinates. Tests with the script loaded assert `getComputedStyle(menu).positionArea === 'none'` plus trigger-relative geometry; tests without it assert the fallback's anchoring.
- [Readiness doesn't detect changed content under an unchanged filename] → Accepted and documented (see the readiness decision). The new-reference case behind this bug is caught.
- [Live scanning on every readiness poll] → mtime-gated parse cache; only `stat` calls per poll. A unit test bounds it: a second call with unchanged templates re-parses nothing.
- [The readiness check flags assets in a local run without Docker that has no built static files] → It is the intended signal; `build:static` fixes it, and the 503 body names the missing files. Unit tests that call `/health/ready` use a static directory fixture.
- [A template scan misses a reference built dynamically] → Templates reference assets as literal `/static/...` paths today. A unit test asserts that the scan finds every `<script src>` and stylesheet in `base.html` and `login.html`.
- [A shared image tag changes how compose names images] → Ansible already builds everything with `build: always`. The tag is overridable, and `docs/admin-guide.md` notes the change.
- [Browser job adds CI time and a new dependency] → One Chromium-only job, pinned Playwright, cached browser download, separate from `fast-tests`. It is covered by the dependency audit.
- [A form inside a popover (label input, extend select) loses focus or submits oddly] → Same pattern already works for the environment rename/extend forms; cover label save and a real HTMX Extend submission (request sent, `closest tr` replaced) in the browser test.
- [`hx-confirm` dialog opened from inside a popover] → Native `confirm()` doesn't light-dismiss the popover before the request is sent; verify Release/Delete/Cancel in the browser test.
- [A swap removes the row, or leaves it without actions, while its menu is open] → The controller's MutationObserver disposes the menu and its listeners whenever the popover leaves the page; the focus hand-back already no-ops when no replacement trigger exists. Tests assert disposal in every case and reopen only when the replacement row still has a trigger.

## Migration Plan

Template, static-script, compose, health and CI changes; deploy as usual (Ansible already rebuilds every service). Developers using compose run `docker compose up --build` once. If they skip it, `/health/ready` and the startup log name the missing assets. Rollback by reverting the commit (restores `<details>` booking menus, `environment_menu.js` and the previous build steps); the new CI check can be made non-required in branch protection if it must be rolled back separately.
