# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working

Whenever possible, use subagents to perform new tasks — delegate to the most specific agent type that fits (e.g. Explore for searches, Plan for design work, general-purpose for multi-step jobs). Handle trivial single-step actions inline where spawning an agent would only add overhead.

## Commands

```bash
# Start all services (postgres, redis, app, worker, beat)
docker compose up

# Run DB migrations (first time or after adding a migration)
docker compose exec app alembic upgrade head

# Run migrations locally (requires local postgres)
DATABASE_URL_SYNC=postgresql+psycopg2://portal:portal@localhost:5432/portal alembic upgrade head

# Install deps for local development
pip install -r requirements-dev.txt

# Run all tests (unit/integration-marked tests are skipped by default — no real Postgres needed)
pytest tests/

# Run a single test file
pytest tests/test_create_booking.py

# Run a single test by name
pytest tests/test_create_booking.py::test_create_booking_returns_pending

# Run the Postgres integration suite (needs a real db; see tests/integration/conftest.py)
TEST_POSTGRES_URL=postgresql+asyncpg://portal:portal@localhost:5433/portal_test pytest -m integration

# Start app locally (requires running postgres + redis)
uvicorn app.main:app --reload

# Start Celery worker locally
celery -A app.infrastructure.celery_app worker -l info

# Start Celery beat locally (TTL enforcement, stale-provisioning reaper)
celery -A app.infrastructure.celery_app beat -l info

# Rebuild Tailwind CSS after changing templates (requires node + npm install)
npm install && npx tailwindcss -i tailwind.input.css -o app/static/css/tailwind.css --minify
```

Static assets (`app/static/`) are build artifacts — generated by the Docker frontend stage and gitignored.
When working locally without Docker, run the Tailwind rebuild command above after adding new utility classes to templates.

Python quality checks (ruff/mypy/bandit) are wired through the `py-review` skill rather than a bare CLI invocation — invoke that skill instead of guessing flags.

## Architecture

This project follows **Clean Architecture** with a strict one-way dependency rule: inner layers have no imports from outer layers.

```
domain → application → infrastructure → presentation
```

The system provisions three kinds of bookable resource behind one `Booking` model: **VM** (Terraform-provisioned, via vCloud Director), **static VM** (pre-existing machine, admin-registered), and **namespace** (pre-existing cluster namespace). Static VMs and namespaces are drawn from an admin-managed pool — reserving one is synchronous (no provisioning step); when the pool is empty the booking is enqueued `QUEUED` and promoted FIFO as resources free up. Bookings can also be ordered as a group: an **Environment** is a parent record owning N child bookings (built from an admin-defined **EnvironmentBlueprint**) that share one TTL and are released together.

### Layer responsibilities

**`app/domain/`** — Pure Python, zero framework imports.
- `entities.py` — dataclasses: `Booking`, `VM`, `User`, `APIKey`, `VMImage`, `HWConfig`, `Namespace`, `StaticVM`, `Role`, `Environment`/`EnvironmentBlueprint`(+`Item`), `Quota`, `BookingAuditEntry`. `Booking` carries many `# deprecated` flat fields kept for backward compatibility alongside the newer `details` (`VMDetails | NamespaceDetails | StaticVMDetails`) and `footprint` (`ResourceFootprint`) value objects — prefer `details`/`footprint` in new code.
- `enums.py` — `BookingStatus`, `ResourceType` (`VM | STATIC_VM | NAMESPACE`), `DriveType` (`SSD | HDD`).
- `booking_status.py` — the `BookingStatus` transition graph (`ALLOWED_TRANSITIONS`, `can_transition`), plus `LIVE_STATUSES`/`LIVE_CHILD_STATUSES` frozensets used for quota counting and pool-availability checks. `Booking.transition_to()` (in `entities.py`) is the enforcement point — raises `IllegalStatusTransitionError` on a disallowed move; a no-op (`old == new`) is allowed.
- `lease.py` — `Lease`, the single home for the TTL/expiry rule: `ttl_minutes == 0` means permanent (far-future sentinel `PERMANENT_EXPIRES_AT` from `constants.py`), otherwise `now + ttl_minutes`. Use `Lease.starting_now()` / `Lease.pending()` / `.extended_by()` rather than hand-rolling expiry math.
- `resource_details.py`, `validation.py`, `exceptions.py` — value objects, shared validators (e.g. `validate_var_names` for Ansible extra-vars keys), and the domain exception hierarchy (`BookingError`, `EnvironmentError`, `NotFoundError`, etc. — routes translate these to HTTP status codes).

Never import SQLAlchemy, FastAPI, or Celery here.

**`app/application/use_cases/`** — One business operation per file: `create_booking` (VM), `reserve_pooled_resource` (shared by static-VM and namespace reservation — the per-type differences live in a `PooledResourceConfig`), `reserve_static_vm`, `book_namespace`, `order_environment`/`release_environment`, `extend_booking`, `release_booking`, `force_release_booking`, `update_booking_label`, `update_environment_name`. Use cases receive a session as a parameter; they do not open sessions themselves. They depend on `app/application/ports.py` Protocols (`BookingRepositoryPort`, `TaskDispatcher`, etc.), never on concrete infrastructure classes, so the DB/Celery can be swapped or faked in tests without touching use-case code. `_permissions.py` (`can_manage` — owner, the dispatcher who created it on the owner's behalf, or an admin) and `_roles.py` are shared helpers, not use cases themselves.

**`app/infrastructure/`** — All framework/driver code:
- `database/models.py` — SQLAlchemy ORM (separate from domain entities; each `repositories/*_repo.py` maps between them)
- `database/session.py` — exposes `AsyncSessionLocal` (used by FastAPI routes via `get_async_session`) and `SyncSessionLocal` (used by Celery workers)
- `repositories/booking_repo.py` — async methods for FastAPI, `sync_*` methods for Celery (both operate on the same ORM models); same async/sync split pattern in `environment_repo.py`. The other repos (`image_repo`, `hw_config_repo`, `namespace_repo`, `static_vm_repo`, `role_repo`, `quota_repo`, `user_repo`, `environment_blueprint_repo`) are async-only (FastAPI side only).
- `terraform/adapter.py` — `TerraformAdapter` Protocol (`apply` / `destroy`, both take an `on_progress` callback and an optional per-call `api_token`)
- `terraform/stub_adapter.py` — dev/test stub: sleeps briefly, returns a fake IP. Selected via `settings.USE_STUB_TERRAFORM` (default `True`).
- `terraform/vcd_adapter.py` — the real adapter: drives Terraform against vCloud Director, one workspace per booking.
- `config/runner.py`, `config/ansible.py` — post-provision VM configuration: SSH in and run an optional bash startup script (`ConfigScriptError`) and/or apply selected Ansible roles (`AnsibleConfigError`). Both are "software" failures that keep the VM (`READY` + `config_failed=True`) rather than failing the booking — only an unreachable VM is an infra failure.
- `crypto.py` — Fernet encryption for Ansible role `secret_vars` at rest (`SECRETS_ENCRYPTION_KEY`); fails closed if a role has secret vars but no key is configured.
- `auth.py` — `get_current_user`/`require_user`/`require_admin` FastAPI dependencies. Two auth methods: `Authorization: Bearer dp_<key>` (API keys, hashed with SHA-256) or a `session_id` cookie backed by a Redis-stored session (bcrypt-hashed passwords). Three roles: `user` < `dispatcher` (may order/release on behalf of another user, #229) < `admin`.
- `celery_app.py` / `celery_dispatcher.py` — the Celery instance (tasks registered via `include=[...]`, `beat_schedule` for the periodic jobs) and `CeleryTaskDispatcher`, the concrete `TaskDispatcher` port implementation. Task modules are imported lazily inside dispatcher methods to avoid import cycles.

**`app/tasks/`** — sync Celery tasks (all use a `_run(work)` helper that opens/closes a short-lived `SyncSessionLocal` per DB operation, so no connection is pinned across a minutes-long `asyncio.run(terraform.apply/destroy(...))` call):
- `provision.py` — `provision_vm_task`: acquires a VCD API-token semaphore slot (Redis lock, `VCD_TOKEN_MAX_PARALLEL` per token) when not using the stub adapter, applies Terraform, then runs post-provision configuration (startup script / Ansible roles) before marking the booking `READY`. Retries up to `PROVISION_MAX_RETRIES`× on unexpected exceptions; `SecretDecryptionError` fails immediately without retrying (a bad encryption key won't fix itself).
- `teardown.py` — `teardown_vm_task`: for pooled resources (namespace/static VM), just flips status to `RELEASED` and promotes the next `QUEUED` booking — no Terraform involved. For VMs, runs `terraform.destroy(...)`. `force=True` (used by admin force-release and startup recovery) marks the booking `RELEASED` even if destroy fails.
- `beat_tasks.py` — `enforce_ttl` / `enforce_environment_ttl` (release expired bookings/environments) and `reap_stale_provisioning` (fail bookings stuck in a non-terminal state past `STALE_PROVISIONING_THRESHOLD_MINUTES`), scheduled via `celery_app.conf.beat_schedule`.

`app/main.py` startup (`lifespan`) seeds the initial admin user, then re-queues provisioning for any booking left mid-flight and forces teardown for any stuck in `RELEASING` after a restart (skipped entirely when `USE_STUB_TERRAFORM=True`).

**`app/presentation/`** — FastAPI routers (`bookings`, `environments`, `admin`, `auth`, `events`, plus JSON-only `api`/`api_bookings`/`api_environments`) + Jinja2 templates (`templates/`, fragments under `templates/partials/`). HTML routes use `Depends(get_async_session)` + `Depends(require_user)`/`require_admin`; `POST /bookings` and the `/api/v1/...` routes do content negotiation (`Accept: application/json` → JSON, otherwise an HTMX HTML fragment). The legacy unversioned `/api/...` routes are mounted alongside `/api/v1/...` for backward compat but excluded from the OpenAPI schema (`include_in_schema=False`), as are all HTML routes — `/docs` only shows the JSON API surface. `middleware/correlation_id.py` binds a request id (echoed on every response, including CSRF rejections) and `middleware/csrf_origin.py` rejects cross-origin state-changing requests by comparing against `settings.BASE_URL`.

### Key patterns

**Async vs sync split** — FastAPI and the domain layer are fully async. Celery workers are sync. Repositories that both use-cases and tasks touch (`booking_repo`, `environment_repo`) expose both: `async def get(...)` for routes and `def sync_get(...)` for tasks. Do not use `asyncio.run()` inside routes; tasks use it exactly once per `TerraformAdapter` call.

**Status transitions are enforced, not assumed** — `BookingStatus` moves through `QUEUED`/`PENDING → PROVISIONING → CONFIGURING → READY/RETRY/FAILED → RELEASING → RELEASED` per the graph in `domain/booking_status.py`. Any new status-changing code path should go through `Booking.transition_to()` or a repository `sync_update_status`/`update_status` call (which apply the same guard) rather than writing `.status` directly.

**Live row updates (SSE, with a polling fallback)** — `GET /events/stream` (`app/presentation/routes/events.py`) pushes booking/environment row updates over Server-Sent Events: `BookingRepository`'s mutating methods (`update_status`/`sync_update_status`, `sync_set_status_message`, `sync_record_progress`, `extend`, `update_label`, `promote_next_queued`/`sync_promote_next_queued`) call `publish_row_changed`/`apublish_row_changed` (`app/infrastructure/events.py`) immediately after their own commit, which `PUBLISH`es to a shared Redis channel. The stream endpoint subscribes to that channel, re-fetches the affected booking/environment per message, applies `can_manage()` for *that connection's own user*, and — only if authorized — emits the same HTML `GET /bookings/{id}/row`/`GET /environments/{id}/row` would return, as a named SSE event (`booking-<id>`/`environment-<id>`) that the row's `sse-swap` attribute picks up. Redis pub/sub has no replay guarantee, so each row also keeps a much slower 60s `hx-get` fallback poll as the safety net — never fully SSE-only.

**Terraform workspaces** — Each VM booking maps to workspace ID `booking-{uuid}` for per-booking Terraform state isolation (Postgres backend, `TF_PG_CONN_STR`). The stub adapter ignores it.

**Quota enforcement** — `quota_repo.get_limits_for_update` + `count_active_resources` (counting `LIVE_STATUSES` bookings) are used together under a row lock so concurrent booking requests can't both slip past the same limit; see `tests/integration/test_quota_concurrent_writes.py`.

**Alembic migrations** — `alembic/env.py` reads `DATABASE_URL_SYNC` from the environment, overriding `alembic.ini`. Always use the sync psycopg2 driver for Alembic, not asyncpg. Migrations live in `alembic/versions/`, one file per change — check `tests/test_migration_chain.py` for the chain-integrity expectation.

**Feature/bugfix history as reference** — `docs/features/` and `docs/bugfix/` each hold one short doc per past change, named after the issue or feature (e.g. `docs/bugfix/374-stuck-releasing-after-restart.md`). When touching an area, check for an existing doc there before re-deriving the reasoning behind current behavior — it's frequently already written down. `docs/decisions/` holds a couple of longer-lived design-decision records (CSRF strategy, vended-credentials-at-rest).

## Coding

Before writing code, think about the design first:

- **Identify the domain model** — what core entities and concepts does this change touch, and where do they belong in the layers (`domain → application → infrastructure → presentation`)?
- **State the invariants** — what must always hold true (e.g. a `Booking` status only moves `PENDING → PROVISIONING → READY / FAILED`)? Make the code enforce them rather than assume them.
- **Choose the right abstraction** — model behaviour behind interfaces (e.g. the `TerraformAdapter` Protocol) so implementations can be swapped without touching callers.
- **Apply design principles** — respect the one-way dependency rule, keep each use case to one business operation, separate async (FastAPI/domain) from sync (Celery) concerns.
- **Minimize special-case handling** — prefer a single general path over branches for edge cases. If you find yourself adding an `if` for a specific input, ask whether the model can be reshaped so the case stops being special.

## Feature Planning

When planning or creating a new feature:

1. Save a feature description document in `docs/features/` covering: goal, what changes (API, CLI, DB migrations), and expected behaviour/edge cases.
2. Ask the user to review the feature description and wait for explicit approval ("ok", "looks good", etc.) before writing any code.
3. Only begin implementation after the user confirms.

When a feature is complete:
- Write tests covering the new behaviour (see **Testing** below).
- Update `docs/admin-guide.md` and `docs/api-reference.md` to reflect any new or changed CLI commands, API endpoints, and workflows.

## Bug Fixing

When fixing a bug, follow the same process as feature planning:

1. Save a bugfix description document in `docs/bugfix/` covering: root cause, what changes, and expected behaviour after the fix.
2. Ask the user to review the bugfix description and wait for explicit approval before writing any code.
3. Only begin implementation after the user confirms.

When a bugfix is complete:
- Write a regression test that fails before the fix and passes after.
- If the fix changes any user-facing behaviour (CLI output, API responses, workflows), update `docs/admin-guide.md` and `docs/api-reference.md` accordingly.

## Git Workflow

- Always create a new branch for every feature or change — never commit directly to main.
- Always start a new branch from a fresh main: `git checkout main && git pull && git checkout -b <branch>`.
- Never force-push to the main branch.
- Never force-push
- Never add `Co-Authored-By: Claude` or any AI co-author line to commit messages.
- Branch naming conventions:
  - Features: `feature/<issue-number>/<short-description>` (e.g. `feature/14/product-group-and-purl`)
  - Bug fixes: `bugfix/<issue-number>/<short-description>` (e.g. `bugfix/13/pypi-missing-licenses`)
